# CLAUDE.md

@AGENTS.md

## Purpose

A Danish insurance comparison website. Users choose which insurances they
want quotes on (12 types, listed in `src/config/forms/insurance-types.ts`:
car, home contents, house, accident and health, travel, holiday home,
MC/ATV/moped, boat, caravan, pet, life, change of ownership), fill out a
multi-step form, and the lead is saved and passed on to insurance partners.
Only insurance: no pension, salary insurance or unemployment funds.

The product is the lead: complete, valid, consented data delivered reliably.
Every module should be judged by whether it improves lead quality,
conversion or compliance.

## Stack

- **Next.js 16** (App Router, Turbopack) with **TypeScript** in strict mode
- **Tailwind CSS v4** and **shadcn/ui** (Radix base, `new-york` style)
- **react-hook-form** and **zod** (v4) for forms and validation
- **Supabase** (Postgres, EU region) as the database, accessed server-side only
- **Vercel** for hosting (functions pinned to `fra1` in `vercel.json`), **GitHub** for code
- Node 22 (`.nvmrc`, `engines` in `package.json`)

## Commands

```bash
npm run dev        # dev server on http://localhost:3000
npm run build      # production build
npm run lint       # ESLint
npm run typecheck  # generate route types + tsc --noEmit
npm run test       # unit tests (Vitest): schema generator and form logic
npm run test:e2e   # end-to-end tests (Playwright) of the quote flow, mobile + desktop
npm run db:push       # apply pending migrations to the DEV Supabase project
npm run db:push:prod  # apply pending migrations to PRODUCTION (after dev)
npm run db:types      # regenerate src/lib/db/types.ts from the dev database
```

Run `lint`, `typecheck`, `test` and `build` before every commit, and
`test:e2e` when the form changes. GitHub Actions (`.github/workflows/ci.yml`)
runs all of them on every pull request and on `main`. The e2e tests mock
`POST /api/leads`, so they need no secrets and never write to a database.

`GET /api/health` reports whether Supabase is configured and reachable
(`supabase`: `ok`, `not_configured` or `error`) and whether the migrations
are applied (`database`: `ok`, `missing_schema`, `error` or `skipped`).

## Workflow

- **Plan first.** At the start of each module, show the plan (files,
  decisions, open questions) and wait for the owner's approval before
  writing any code.
- **Branch and PR.** Work on a feature branch and open a pull request into
  `main`. `main` is the production branch: Vercel deploys it automatically.
- **Merge without asking (owner, 2026-11-10).** When a piece of work is
  done, open the PR and merge it yourself (squash) once the GitHub checks
  are green and the change is verified locally; then bring `preview` up to
  date. Do not ask first. Exceptions that still need the owner's OK in the
  conversation: production database migrations or writes, and anything
  the checklist marks as a launch blocker being switched on (e.g. the
  brand domain). After a squash merge, bring the work branch up to date
  with `git merge origin/main` (no force push).
- **Finish properly.** A module is done when `lint`, `typecheck` and `build`
  pass, the result is verified in the running app, the module status below
  is updated, and the PR is merged.
- **Show visible changes on the fixed preview address.**
  `https://test.nemforsikringstilbud.dk` is a Vercel Preview domain bound
  to the `preview` branch. After pushing a change the owner can see (pages,
  form, copy, design), also push it there (`git push origin HEAD:preview`,
  owner's permission 2026-11-10) and point the owner to that address. No
  screenshots (owner, 2026-11-10). If the push is rejected because
  `preview` has other history (e.g. after a squash merge, or another
  session's branch), the owner allows replacing its content (2026-11-10).
  Do it without a force push: add a commit on top of `origin/preview`
  with the tree of `HEAD`
  (`git commit-tree HEAD^{tree} -p origin/preview -p HEAD -m "..."`) and
  push that commit to `preview` normally. `preview` is never merged; `main` stays the
  production branch.
- **Vercel only builds `main` and `preview`.** `vercel.json` disables
  deployments for `claude/**` branches (owner, 2026-11-10), because builds
  queue one at a time on Hobby. GitHub Actions still runs every check on
  pull requests.
- **End with a summary:** what was built, and what the owner must do
  themselves (keys, dashboards, manual steps).
- **Keep `docs/huskeliste.md` current.** Whenever something needs the
  owner, the partners or legal review (wording, option lists, legal
  questions, accounts), add it there instead of blocking on it, and move
  settled questions to "Besluttet". It is the one list the owner works
  from, so it is written in Danish (the only Danish doc).
- **Current mode (owner, 2026-11-01, confirmed 2026-11-10): build the
  foundation first.** Build the backend and the website until they run;
  the practical things (company details, payments, legal review, keys,
  domain, partners) go in the checklist and are done at the end. Keep
  building module after module without waiting for plan approval, using
  sensible defaults and logging open questions in the checklist. Design,
  layout and copy are reviewed later. Still ask before production
  migrations (merges: see "Merge without asking").

## Working with the owner

- Be critical. Push back on bad ideas and point out risks and trade-offs
  instead of agreeing by default. Give a recommendation, not a menu.
- Don't use em-dashes in replies or docs.
- Reply in the language the owner writes in (Danish or English). Code,
  comments and docs stay in English.

### Owner requirement: lead quality back to Meta (modules 7 and 8)

Ads run on Meta, and Meta must optimize for leads that turn out *good*,
not just for any lead. So:

- **Module 7** sends a `Lead` event to Meta both from the browser (Pixel)
  and from the server (Conversions API), deduplicated with a shared
  `event_id`, and only with the user's marketing/tracking consent. Store
  per lead what is needed to match it later: the `event_id`, the click id
  (`fbclid` / `_fbc`), the browser id (`_fbp`) and the consent state.
- **Module 8** gets each lead's outcome back from the partners (e.g.
  contacted, quoted, sold) and sends the good ones to Meta as a
  server-side conversion event for the same lead, so campaigns can be
  optimized for lead quality.

Design data and APIs so this feedback loop is possible; do not drop the
identifiers it needs.

## Rules

1. **One module at a time.** Only build what the current module asks for.
   If something from a later module seems necessary, stop and ask.
2. **The form is driven by configuration.** Fields per insurance type are
   data in `src/config/forms`, not hardcoded JSX. Adding or changing a field
   should mean editing config, not components.
3. **One zod schema, used in frontend and backend.** Schemas are *generated*
   from the form config by a single function in `src/lib/schemas`. The client
   form (via `@hookform/resolvers/zod`) and the server endpoint that receives
   the lead import the same schema. Never hand-write a second copy, and never
   trust client-side validation alone: the server always re-validates.
4. **API keys only on the server.**
   - Secrets are read only through `src/lib/env/server.ts`, which imports
     `server-only`. Importing it from client code fails the build. Keep it
     that way: any new module that reads secrets must also import
     `server-only`.
   - Never prefix a secret with `NEXT_PUBLIC_`. Anything with that prefix is
     shipped to the browser.
   - There is no browser Supabase client. All reads and writes go through our
     own server endpoints, using `getSupabaseServerClient()`. The publishable
     (anon) key is the only key allowed in frontend code, and only if a browser
     client is deliberately introduced together with strict RLS policies.
   - Enable RLS on every table with no policies for `anon`/`authenticated`,
     and revoke all their privileges, so the publishable key can read or
     write nothing.
   - External integrations (address, BBR, license plate) are called from the
     server, never directly from the browser.
5. **Mobile first.** Design and test at ~375px width first, then scale up
   with `sm:`/`md:` breakpoints. Tap targets at least 44px tall.
6. **Danish for users, English for code.** All user-facing text (labels,
   errors, buttons, emails, metadata) is in Danish. Code, identifiers,
   comments, commit messages and docs are in English.

7. **Stay a lead service, not an insurance distributor.** The model fits
   the exclusion in lov om forsikringsformidling § 1, stk. 3, nr. 3 (mere
   provision of data on potential policyholders to insurers), so it needs
   no licence from Finanstilsynet, only as long as we: give no advice or
   "you should" suggestions, show no prices, rankings or product
   comparisons, never call ourselves a comparison service
   ("sammenligningstjeneste"), do not collect or present quotes, do not
   help fill in insurers' applications, and are paid per lead, not per
   sale. General information about insurance types is fine. Keep pension
   and savings products out, and never ask about health or family
   history, or any other special category under GDPR art. 9 (e.g. trade
   union membership), even if a competitor does. Stop and ask the owner before building anything that crosses
   this line. Background: `docs/huskeliste.md` (Finanstilsynet).

## Conventions and gotchas

- **Next.js 16 differs from older versions.** Read the bundled docs in
  `node_modules/next/dist/docs/` before using an API you are unsure of.
- **Cache Components is enabled** (`next.config.ts`). A `GET` route handler
  or page that reads no runtime data is prerendered at build time. Call
  `await connection()` (from `next/server`) in handlers that must run per
  request, as `/api/health` does.
- **shadcn/ui** components live in `src/components/ui` and are added with
  `npx shadcn@latest add <name>`. They use the `cn` package (shadcn's
  replacement for clsx + tailwind-merge) via `@/lib/utils`. Prefer composing
  them over editing them. If you do edit one, keep the change small.
- **Bot protection (Vercel BotID).** `src/instrumentation-client.ts` lists the
  protected routes and the route calls `checkBotId()` first. Keep the two in
  sync. BotID only works on Vercel: in `next dev` it always passes, `curl`
  against production is blocked (403), so test from a page in the app. The
  browser part is only loaded on Vercel and in dev (`NEXT_PUBLIC_BOTID_ENABLED`
  in `next.config.ts`), so a local `next start` (e2e tests) works.
- **Env vars** are validated lazily, so the app builds and runs without keys.
  Code that needs Supabase should call `getSupabaseServerClient()`, which
  throws a clear error if keys are missing or invalid.
- **Personal data (GDPR).** Leads contain personal data. Keep it in the EU
  (Supabase EU region, Vercel `fra1`), don't log it, and collect only what
  the partners need.
